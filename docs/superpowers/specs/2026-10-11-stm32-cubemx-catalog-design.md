# STM32 MCU catalog and CubeMX linker script design

Date: 2026-10-11. Scope: STM32 MCUs supported by the locally installed STM32CubeMX 6.18.0. STM32MP is excluded by the user's later instruction.

## Goal and acceptance boundary

The workbench shall list every concrete STM32 MCU target in the pinned CubeMX catalog, select the correct compiler and debug metadata for that target, and, **when it supplies the linker script**, use bytes matching a script generated by CubeMX for that target and supported build context. Project-owned or explicitly selected scripts remain the user's responsibility and are identified as such in the UI and log. The application must work offline and must not require CubeMX on the user's machine. ST-Link V2 and CMSIS-DAP adapters shall be usable for firmware flashing through OpenOCD where a target driver exists. Unsupported target/adapter combinations must fail explicitly before programming.

The catalog is a versioned snapshot, not a claim about future CubeMX releases. Updating CubeMX requires a reproducible catalog refresh and verification. The initial snapshot source is `D:/Soft/STM32CubeMX` version 6.18.0. Its `db/mcu/families.xml` contains 2666 non-MP entries and 1643 distinct non-MP RPNs; the bundled CubeIDE linker database contains 317 `.ld` files. These are inventory counts, not proof that all variants have been mapped or that database files equal final generated output.

## Approaches considered

1. **Recommended: generated, versioned offline catalog.** Generate representative STM32CubeIDE projects with the pinned CubeMX, capture their exact `.ld` bytes, map every concrete CubeMX target and context to a captured file, and package the catalog with the plugin. Content-addressed storage may deduplicate identical files without changing the bytes returned to a project. This gives offline use and a testable coverage claim, at the cost of a catalog refresh process.
2. **Ship CubeIDE's internal linker database directly.** Small initial payload, but it is not yet proven that those 317 source files are byte-identical to the output CubeMX writes for every selected target/context. It cannot be the sole acceptance basis.
3. **Calculate memory sizes and synthesize `.ld`.** Small payload but contradicts the required exact CubeMX output and fails on split memory, TrustZone and multicore devices. Reject.

## Source and generation pipeline

An offline packaging tool shall enumerate each concrete MCU entry from CubeMX's device database, excluding MP entries. It shall record the exact reference name, RPN, family, core/context, CubeMX version, and source database identity. It shall invoke CubeMX's documented script mode with the STM32CubeIDE toolchain to create generated projects in disposable workspace directories. The tool shall collect every generated `.ld` for each device and applicable context, then record relative names, byte counts and SHA-256 values. The supported context dimensions are the generated core (for example CM7/CM4), Secure or NonSecure image where CubeMX offers that split, and CubeMX's generated FLASH or RAM link variant where available. Generation uses CubeMX defaults for memory layout, minimum heap/stack, boot address and other project options; the manifest stores the canonical generation script and relevant `.ioc`/project settings for reproduction. User-customized CubeMX memory management, heap/stack or boot layout is outside the packaged default: that project must use its own generated `.ld` or explicitly import one. A multi-core or Secure/NonSecure target may have more than one linker artifact; the catalog key includes target plus context dimensions, and the UI must require a context when several are valid. No first-file choice.

The packaging tool may use CubeIDE's bundled linker database as an optimization only after comparing its bytes against actual CubeMX output for each mapping. Firmware packages and generator versions used in generation shall be recorded. The target list and family come from CubeMX's device database; core, FPU and memory reporting fields come from the corresponding device XML and generated toolchain metadata; compiler CPU/ABI/FPU flags and preprocessor defines are extracted from the actual generated STM32CubeIDE project or generated Makefile/CMake files and checked against device metadata. Do not guess these flags from family names. OpenOCD target mapping is a separate, versioned compatibility table checked against the packaged/configured OpenOCD scripts and representative initialization tests; absence of a driver is recorded as a flashing limitation, not filled with an F1 fallback. Any device whose project cannot be generated, whose context cannot be determined, whose compiler metadata is missing or contradictory, or whose script cannot be mapped is a catalog coverage failure; the package must not claim complete coverage until the failure is resolved. A manifest shall include catalog version, source versions, each target/context mapping, compiler metadata provenance, script hash, and an explicit coverage report. Preserve ST copyright/license notices in packaged files and include the applicable license text in distribution materials; confirm release obligations before publishing.

## Runtime components and data flow

`STM32ProfileManager` becomes a strict catalog lookup keyed by exact CubeMX reference name, with an explicit alias from a shorter RPN only when it resolves uniquely. Unknown or ambiguous names return an error; there is no F103 fallback. Profiles hold the target's family, core, ABI/FPU flags, preprocessor defines, memory reporting data, OpenOCD target mapping and available build contexts. Do not derive linker memory layout from these fields.

`LinkerScriptRepository` reads the bundled manifest and payload, verifies the selected script hash, and copies the original bytes to a workspace-controlled path only when the project needs a supplied script. It must not normalize line endings or rewrite text. Project-owned or explicitly selected `.ld` files take priority and are never overwritten. If the project contains several candidate scripts and none is selected, ask the user to choose. The exact script source, target and context must be visible in the build log. If the selected script is unavailable or fails hash validation, stop before writing the Makefile.

`MakefileGenerator` receives a resolved script path; it no longer invokes `generateLinkerScript` for supported targets. Existing projects remain buildable with their own custom `.ld`. An old SmileCodeIDE generated `.ld` is not silently replaced: show the old source and require explicit migration to the CubeMX script, then preserve the original as a backup. This avoids erasing existing local changes while eliminating the incorrect auto-generation path for new projects.

The chip selector must support search/filtering across the full catalog and display full reference name plus context. Persist exact target and context, not a fuzzy chip prefix. For multiple cores, create independent build outputs and link selections. The first implementation plan should separate catalog generation, runtime selection, and probe validation into reviewable stages, with an end-to-end gate across them.

## Flash path

Use the current OpenOCD interface configs `interface/stlink.cfg` for ST-Link V2 and `interface/cmsis-dap.cfg` for CMSIS-DAP, allowing explicit overrides. The selected physical adapter and serial must be passed to OpenOCD; reject an offline or mismatched probe before starting. Select a target config through an explicit tested device/family mapping and verify that the configured OpenOCD installation actually provides both scripts. Newer MCUs without an OpenOCD target driver must be shown as unsupported for that driver with a clear reason; do not fall back to F1. Preserve address validation, verify and reset options. Do not claim hardware flashing coverage merely from catalog coverage.

The existing UI already lists both drivers and the core already builds OpenOCD arguments. The implementation should focus on end-to-end selection, target mapping, error handling and hardware validation, not duplicate driver entries. The GDB-server adapter choice is a separate follow-up unless needed by flashing tests.

## Verification and release gates

- Produce a machine-readable report proving every non-MP CubeMX entry has exactly one or more explicit target/context mappings, complete compiler metadata with source provenance, and every referenced script passes SHA-256 verification. Report counts by family, missing entries and generation failures.
- Byte-compare each packaged script against the CubeMX-generated `.ld` artifact from the same target/context. Check representative single-core, split-RAM (H743VI), dual-core, TrustZone and newest-family devices manually as well.
- Test exact and ambiguous target lookup, no F103 fallback, context selection, project-owned-script priority, old auto-script migration, byte preservation and hash-failure behavior. Use a real H743VI startup and build to verify the chosen CubeMX script resolves `_estack` and produces a plausible initial SP.
- Test OpenOCD command construction for ST-Link V2 and CMSIS-DAP, serial selection, missing interface/target scripts, unknown target and offline adapter. Execute real flashing with each adapter on a compatible board when the hardware is available; report untested hardware separately.
- Build the standalone application and plugin, run the relevant Qt tests, then inspect the deployed package to ensure the manifest, scripts and license notices are present. No release or full-coverage claim before all catalog checks pass.

## Known implementation constraints

The current worktree contains extensive pre-existing edits; the plugin tree is untracked in the current Git state. Implementation must avoid overwriting unrelated changes. CubeMX 6.18.0 and CubeMX2 1.1.0 are both installed; this design deliberately pins CubeMX 6.18.0 and does not mix their catalogs. A changed firmware package or generator version can change script bytes, so the manifest must preserve generation provenance. The CubeIDE linker database's H743XI FLASH template uses separate DTCMRAM, RAM_D1, RAM_D2, RAM_D3 and ITCMRAM regions and places `_estack` at the end of RAM_D1; compare actual CubeMX output before adopting it as the H743VI artifact.
